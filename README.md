# 基于 Java 的网咖管理系统的设计与实现

> 毕业论文配套系统 · 作者：胡政宇

## 一、项目简介

面向中小网咖的单体管理系统，采用 B/S 三层架构，按**会员、收银员、管理员**三种角色组织功能，
共 **25 个功能模块**，覆盖会员注册充值、机位开台与计费结算、商品销售、设备租赁、
在线预约与营收统计等完整经营流程。

## 二、技术栈

| 层次 | 技术 |
|---|---|
| 后端框架 | Spring Boot 3.3.5 |
| 持久层 | MyBatis-Plus 3.5.7（MyBatis 增强框架） |
| 数据库 | MySQL 8.0 |
| 模板引擎 | Thymeleaf |
| 前端 | Bootstrap 5.3.3 + ECharts 5.5.1 |
| 构建 | Maven 3.9.9（编译目标 Java 17） |

前端静态资源（Bootstrap、ECharts）已下载至 `src/main/resources/static/vendor/`，
**不依赖 CDN**，断网环境下页面仍可正常显示。

## 七、核心业务规则

系统中有四条贯穿全局的规则，所有代码与统计口径都遵循它们。理解这四条即理解本系统。

### 1. 计费规则

- **计费时长向上取整到 5 分钟**，不满 5 分钟按 5 分钟计。
- **折扣取更优惠者**：实际折扣 = min(区域会员折扣, 会员等级折扣)。
  不采用两者相乘 —— 相乘会得出 0.855 这类难以向顾客解释的数字。
- **自动取优**：按小时与包时套餐分别计算，取金额更低者；
  超出套餐的部分仍按小时计。顾客无需自行判断哪种更划算。

计费规则存于 `billing_rule` 表，管理员调价后立即生效，**改数据不改代码**。

### 2. 机位状态机

机位只有三种状态：`FREE`（空闲）、`USING`（使用中）、`MAINTENANCE`（维护中）。

- 状态流转的合法性由 `SeatService` 统一校验，非法跳转（如维护中直接开台）会被拒绝。
- 所有状态变更使用 **CAS**（带条件的 UPDATE + 判断受影响行数），
  避免两名收银员同时给同一机位开台。
- **不设「已预约」状态**：预约是否占用机位由时段重叠检测判断，
  否则「预约今晚 8 点」会导致该机位从现在起就无法使用。

### 3. 下机结算是一个整体事务

算费 → 扣款 → 写账户流水 → 更新上机记录 → 释放机位，五步在**同一事务**内完成。
任一步失败整体回滚，不会出现「钱扣了但机位没释放」或「机位释放了但钱没扣」。

### 4. 账户流水是余额变动的唯一入口

任何业务都不得直接修改 `member.balance`，必须调用 `BalanceService`，
由它统一完成「加行锁读取 → 校验并更新余额 → 写入流水」。

由此保证一个恒等式始终成立：

```
SUM(balance_record.change_amount) == member.balance
```

一旦出现差额即说明账务异常。管理员端「会员详情」页会直接展示该差额，
这是验证结算数据一致性的直接依据。

> 资金操作用的是**悲观锁**（`SELECT ... FOR UPDATE`）而非乐观锁，
> 因为流水中要记录「变动前余额 / 变动后余额」，这两个值必须与本次变动严格对应。

### 统计口径

| 收入类型 | 确认时点 |
|---|---|
| 上机收入 | 结算时间 `end_time`（跨天订单归入实际下机那天） |
| 商品收入 | 挂账的按所属上机记录的结算时间；前台直购的按记账时间 |
| 租赁收入 | 归还时间（租金在归还时才确定租期） |
| 充值金额 | 单独统计，属于**预收款，不计入营业收入** |

全系统保持口径一致，因此「上机 + 商品 + 租赁 = 营业收入合计」恒成立。

## 九、常见问题

**Q：启动提示「Port 8080 was already in use」**
换一个端口：在 `--server.port=8081` 中指定其他端口，或先结束占用 8080 的进程。

**Q：启动报「Access denied for user 'root'」**
`application.yml` 里的数据库密码不对，改成你自己的 MySQL 密码。

**Q：某区域机位结算时报「尚未配置计费规则」**
计费规则表里的区域名称必须与机位表的区域名称**完全一致**。在管理员端
「机位管理」与「计费规则配置」两页核对名称是否相同。

**Q：想恢复演示数据到初始状态**
重新执行第四节的第 1 步即可，`schema.sql` 会先删表再重建。

**Q：部署在中文路径下会不会有问题**
项目已按中文路径（`E:\论文\网咖管理系统`）实际运行验证通过，可以正常使用。

## 十一、补齐的业务与账号保护

- 修改会员资料、状态、密码仅更新对应字段，不携带余额与押金。
- 按会员串行化资金与经营操作，商品挂账与结算锁定同一上机记录并读取当前订单，避免并发漏收；同会员并发开不同机位只允许一次成功。
- 手工机位状态只允许空闲与维护互转，使用状态由开台、结算驱动；机位资料修改不覆盖状态。
- 普通开台校验当前有效预约的会员归属；核销直接在原预约机位为原会员开台，两步在同一事务中完成。
- 核销可在预约开始前15分钟至开始后15分钟办理，最迟不超过预约结束；超时未到店每分钟自动过期。未来预约不会提前锁死机位，当前上机超时到未来预约时段时需前台协调下机。
- 冻结账户拒绝新增充值、开台、商品和租借业务，但允许已有上机结算及已有设备归还。
- 零押金设备正常租还，租金与押金拒绝负数、超过两位小数；库存不能为负数。
- 套餐时长与价格同时留空可取消套餐；统计区间统一作用于汇总、趋势、区域上机收入及热销商品。
- 商品费用明细支持分页。公告支持发布、编辑、撤下及删除；删除使用独立状态保留历史内容，常规列表不可见且不能重新发布。
- 新密码采用 BCrypt；历史MD5演示账号在成功登录后自动迁移。原密码及演示账号不变，不需要重建数据库。
- 每次受保护请求校验账号状态、角色和密码凭据标记；停用、降权或重置密码后旧会话失效。
- 全部POST表单带有会话CSRF令牌，登录注册同样受保护，退出使用POST。脚本提交也必须先读取页面令牌。
- 再次自检补齐：权限依据MVC实际匹配路由校验，阻止编码URL越权；充值先锁会员避免并发锁升级死锁；普通开台同步核销本人当前预约；开卡显式密码至少6位。
- 2026-10-07本轮验证：58项JUnit测试、40项真实HTTP检查通过，新JAR已重新打包。

## 十二、实际使用范围

会员在线充值为明确标注的模拟流程，不产生真实支付。真实支付宝或微信支付需要商户账号、签名密钥、回调地址与平台联调，不包含在本地演示实现中。

这是B/S经营管理系统，未接入网咖终端控制代理，不会远程关机或自动强制终止上机。也未进行生产环境负载测试；复杂审计查询与接口限流可作为后续优化。

上述业务修复沿用原14张表，无需删库重建。MySQL测试连接使用独立副本，修复验证不改现有演示数据。
